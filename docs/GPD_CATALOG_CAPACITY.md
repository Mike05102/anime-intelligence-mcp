# 一般商品24万件の容量比較

2026-11-26に、ネットワーク待受けを無効にした隔離PostgreSQL 17で一般商品24万件、全24カテゴリー各1万件を生成した。商品、販売業者、GTINは容量試験専用データ。本番データをコピーせず、SupabaseやWorkerへ送信していない。

現行方式はテスト用 `products` に本番事前診断で確認した構成に近い列・索引を追加し、既存のカタログ移行を適用した。新規商品には現行Worker相当のGTIN、メーカー、日英名欄、出典、型式、バリエーションと市場観測を入れた。新規行だけを挿入し、通常のVACUUM後に `pg_table_size`、`pg_indexes_size`、`pg_total_relation_size` を測定した。既存商品との混在、更新履歴、WAL・一時ファイルの占有は別途評価が必要。

軽量方式も同じ商品の名前・識別子と件数を使用する。比較対象には次を含む。

- 同じ表・索引を使い、市場観測のJSONフィールドを商品行から除いた場合。観測を別に保持する容量を、この行には含めない。
- GTINの固定幅値、既存呼び出し向けに残すUUID、カテゴリー・メーカー・出典の辞書、確認時刻、表示名に分けた専用表。索引はGTIN、UUID、カテゴリー＋確認時刻。
- 専用表の表示名にトライグラム検索を加えた場合。複数言語で別の名称がある行の追加表示名や既存検索との互換層は未計上。
- 上記に現在の販売条件を各商品1件追加した場合。仕向け国、通貨、在庫、金額、販売ページURL、観測時刻と索引を保持する。履歴の全件保存は想定しない。

実行には Node.js、隔離された PostgreSQL 17 の `initdb` と `pg_ctl`、`pg_trgm`、テストと同じNodeの `pg` ライブラリが必要。空き容量を確保してから実行する。スクリプトは一時ディレクトリにDBを作り、同じディレクトリのUnixソケットだけに接続し、終了時に片付ける。

```sh
GPD33_PG_MODULE=/path/to/node_modules/pg/lib/index.js \
  node scripts/gpd33_catalog_capacity.mjs /usr/lib/postgresql/17/bin
```

## 本番の測定値との比較方法

2026-11-26の読み取り専用集計では、`api_events` 全体を除いた本番DBは **316,607,635バイト**、既存 `products` は **284,909,568バイト・124,289行**。既存商品の全行を保護し、今回の24万件を追加する保守的な比較とする。既存行のうち検証済み一般商品として再利用できる数は、別途DBの実件数で確認する。

追加前に残る領域は、イベントを仮に0バイトとした場合でも400 MBまで **83,392,365バイト**、500 MBまで **183,392,365バイト**。追加する一般商品1件あたり、それぞれ約347バイトと764バイト。実際に保持する決済・収益データ、作業領域、索引の肥大、複数地域の販売条件は、この余裕をさらに使う。容量の上限は10進バイトで比較し、通常運用の停止基準には400,000,000バイトを使う。

## 計測結果

PostgreSQL 17.12。1 MBは1,000,000バイト。商品表増分には索引を含め、専用表方式は辞書も含む。「イベントなしの合計」は本番の非イベント領域316,607,635バイトと隔離環境の増分を足した試算。保持する決済記録の実容量と本番での更新負荷は未計上。

| 方式 | 24万件分の増分 | イベントなしの合計 | 400 MBまでの残り | 500 MBまでの残り |
|---|---:|---:|---:|---:|
| 現行商品行・市場JSON・日英の名称索引 | 483.451 MB | 800.059 MB | −400.059 MB | −300.059 MB |
| 同じ表から市場JSONを削った商品行 | 382.640 MB | 699.248 MB | −299.248 MB | −199.248 MB |
| 専用表・正確な識別子検索 | 77.603 MB | 394.210 MB | 5.790 MB | 105.790 MB |
| 専用表・表示名トライグラム検索あり | 111.878 MB | 428.486 MB | −28.486 MB | 71.514 MB |
| 専用表・正確な識別子検索・販売条件1件/商品 | 130.646 MB | 447.254 MB | −47.254 MB | 52.746 MB |
| 専用表・表示名検索・販売条件1件/商品 | 164.921 MB | 481.529 MB | −81.529 MB | 18.471 MB |
| 上の販売条件を約1割更新して通常のVACUUMを実行 | 168.698 MB | 485.305 MB | −85.305 MB | 14.695 MB |

現行方式は表310,796,288バイト、索引172,654,592バイト。市場観測を除いた場合も、同じ列と索引を使うため240,000件の追加には足りない。専用表の表示名検索は、上記の試験で34,275,328バイトの追加。販売条件24万行の表・索引は53,043,200バイトで、約1割の更新後は56,819,712バイト。通常のVACUUM後も3,776,512バイトの差が残った。同じ商品に地域別の販売条件を複数保存した場合はさらに増える。

内部の40件参照をUTF-8 JSONに変換すると、現行の名称2欄とメタデータを含む形は44,929バイト、専用表の識別用フィールドは14,267バイトだった。結果の識別情報を先に返して、販売条件は需要時に別照会する設計を評価できる。この値は異なる投影のシリアライズ比較であり、HTTPヘッダー、圧縮、実トラフィックは測定対象外。

## 移行判断と次の隔離検証

現行方式への24万件一括追加は500 MBを超える。専用表の正確な識別検索だけなら400 MBまで計算上5.790 MBの余裕があるが、保護対象イベントと販売条件を載せる余裕は確認できない。全商品に販売条件と名前検索を持たせる試験は、イベントを除いても運用基準400 MBを超えた。500 MBまでの残り14.695 MBは今回の更新までで、将来の更新や作業領域の安全を証明していない。

次の検証では、既存UUIDと既存APIの参照を維持しながら、固定幅GTINと元のバーコード形式の復元、製品変更・消滅、証拠の再取得、旧商品との衝突を確認する。すべての商品に同じ検索索引と最新オファーを追加した方式のほか、需要のあるオファーだけを期限付きで保持する方式と、多言語タイトルを必要な場合だけ保存する方式を比較する。保護対象の移動や削除はこの試験の対象外。

この試験はUNLOGGEDの合成テーブルを使用し、ローカルのWAL増加を測定から外した。実行環境に `pg_dump` と `psql` がないため、24万件の論理バックアップ復元、WALと物理空き容量の見積もり、本番書き換え時のロック時間は未検証。通常テーブルでの負荷、復元後の件数・索引サイズ、保護対象の一致を別途確認してから本番変更を検討する。
