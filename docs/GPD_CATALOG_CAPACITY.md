# 一般商品24万件の容量比較

2026-11-26に、ネットワーク待受けを無効にした隔離PostgreSQL 17で一般商品24万件、全24カテゴリー各1万件を生成した。商品、販売業者、GTINは容量試験専用データ。本番データをコピーせず、SupabaseやWorkerへ送信していない。

現行方式はテスト用 `products` に本番事前診断で確認した構成に近い列・索引を追加し、既存のカタログ移行を適用した。新規商品には現行Worker相当のGTIN、メーカー、日英名欄、出典、型式、バリエーションと市場観測を入れた。新規行だけを挿入し、通常のVACUUM後に `pg_table_size`、`pg_indexes_size`、`pg_total_relation_size` を測定した。既存商品との混在、更新履歴、WAL・一時ファイルの占有は別途評価が必要。

軽量方式も同じ商品の名前・識別子と件数を使用する。比較対象には次を含む。

- 同じ表・索引を使い、市場観測のJSONフィールドを商品行から除いた場合。観測を別に保持する容量を、この行には含めない。
- GTINの固定幅値、既存呼び出し向けに残すUUID、カテゴリー・メーカー・出典の辞書、確認時刻、表示名に分けた専用表。索引はGTIN、UUID、カテゴリー＋確認時刻。
- 専用表の表示名にトライグラム検索を加えた場合。複数言語で別の名称がある行の追加表示名や既存検索との互換層は未計上。
- 上記に現在の販売条件を各商品1件追加した場合。仕向け国、通貨、在庫、金額、販売ページURL、観測時刻と索引を保持する。履歴の全件保存は想定しない。

実行には Node.js、隔離された PostgreSQL 17 の `initdb` と `pg_ctl`、`pg_trgm`、テストと同じNodeの `pg` ライブラリが必要。空き容量を確保してから実行する。スクリプトは一時ディレクトリにDBを作り、同じディレクトリのUnixソケットだけに接続し、終了時に片付ける。

```sh
GPD33_PG_MODULE=/path/to/node_modules/pg/lib/index.js \
  node scripts/gpd33_catalog_capacity.mjs /usr/lib/postgresql/17/bin
```

## 本番の測定値との比較方法

2026-11-26の読み取り専用集計では、`api_events` 全体を除いた本番DBは **316,607,635バイト**、既存 `products` は **284,909,568バイト・124,289行**。既存商品の全行を保護し、今回の24万件を追加する保守的な比較とする。既存行のうち検証済み一般商品として再利用できる数は、別途DBの実件数で確認する。

追加前に残る領域は、イベントを仮に0バイトとした場合でも400 MBまで **83,392,365バイト**、500 MBまで **183,392,365バイト**。追加する一般商品1件あたり、それぞれ約347バイトと764バイト。実際に保持する決済・収益データ、作業領域、索引の肥大、複数地域の販売条件は、この余裕をさらに使う。容量の上限は10進バイトで比較し、通常運用の停止基準には400,000,000バイトを使う。

## 計測結果

PostgreSQL 17.12。1 MBは1,000,000バイト。商品表増分には索引を含め、専用表方式は辞書も含む。「イベントなしの合計」は本番の非イベント領域316,607,635バイトと隔離環境の増分を足した試算。保持する決済記録の実容量と本番での更新負荷は未計上。

| 方式 | 24万件分の増分 | イベントなしの合計 | 400 MBまでの残り | 500 MBまでの残り |
|---|---:|---:|---:|---:|
| 現行商品行・市場JSON・日英の名称索引 | 483.451 MB | 800.059 MB | −400.059 MB | −300.059 MB |
| 同じ表から市場JSONを削った商品行 | 382.640 MB | 699.248 MB | −299.248 MB | −199.248 MB |
| 専用表・正確な識別子検索 | 77.603 MB | 394.210 MB | 5.790 MB | 105.790 MB |
| 専用表・表示名トライグラム検索あり | 111.878 MB | 428.486 MB | −28.486 MB | 71.514 MB |
| 専用表・正確な識別子検索・販売条件1件/商品 | 130.646 MB | 447.254 MB | −47.254 MB | 52.746 MB |
| 専用表・表示名検索・販売条件1件/商品 | 164.921 MB | 481.529 MB | −81.529 MB | 18.471 MB |
| 上の販売条件を約1割更新して通常のVACUUMを実行 | 168.698 MB | 485.305 MB | −85.305 MB | 14.695 MB |

現行方式は表310,796,288バイト、索引172,654,592バイト。市場観測を除いた場合も、同じ列と索引を使うため240,000件の追加には足りない。専用表の表示名検索は、上記の試験で34,275,328バイトの追加。販売条件24万行の表・索引は53,043,200バイトで、約1割の更新後は56,819,712バイト。通常のVACUUM後も3,776,512バイトの差が残った。同じ商品に地域別の販売条件を複数保存した場合はさらに増える。

内部の40件参照をUTF-8 JSONに変換すると、現行の名称2欄とメタデータを含む形は44,929バイト、専用表の識別用フィールドは14,267バイトだった。結果の識別情報を先に返して、販売条件は需要時に別照会する設計を評価できる。この値は異なる投影のシリアライズ比較であり、HTTPヘッダー、圧縮、実トラフィックは測定対象外。

## 需要のある販売条件だけを期限付きで保持する試験

全24カテゴリーの240,000件とGTIN・UUIDの対応を保持し、販売条件だけを商品全体の1%、5%、10%に制限した。1商品あたり1件、保存期限24時間、6時間ごとに4分の1を期限切れとして入れ替え、4回ごとに通常のVACUUMを実行した。12回の入れ替え後も、商品の件数、カテゴリー数、GTINとUUIDの組のチェックサムは一致した。

| 販売条件の上限 | 初期サイズ | 3日目のVACUUM後 | イベントなしの合計 | 400 MBまでの残り | 500 MBまでの残り |
|---|---:|---:|---:|---:|---:|
| 2,400件（1%） | 0.705 MB | 1.507 MB | 395.210 MB | 4.790 MB | 104.790 MB |
| 12,000件（5%） | 2.982 MB | 6.783 MB | 400.486 MB | −0.486 MB | 99.514 MB |
| 24,000件（10%） | 5.808 MB | 13.255 MB | 406.957 MB | −6.957 MB | 93.043 MB |

初期サイズと3日目のサイズは販売条件の表・索引のみ。合計には今回の識別表・辞書77,094,912バイトと、本番の非イベント領域を含む。初回試験の識別表・辞書の計測値は77,602,816バイト。販売条件を1%に絞った場合でも、保護対象イベント、将来の肥大、移行時の作業領域を含めた本番400 MB達成は未検証。販売条件を5%または10%に絞る試算でも、イベントを除いた合計で400 MBを超えた。

同じ試験DB内の別スキーマに24万商品、辞書、5%の販売条件12,000件をSQLでコピーした。全行を双方向に比較し、商品UUIDと辞書・商品への外部キーの一致を確認した。

```sh
GPD33_PG_MODULE=/path/to/node_modules/pg/lib/index.js \
  node scripts/gpd33_catalog_capacity.mjs /usr/lib/postgresql/17/bin \
  --demand-only --logical-copy
```

## カテゴリー順の物理配置と省容量索引

識別表の初回投入をカテゴリー順に揃え、カテゴリーと確認時刻の複合B-treeを16ページ単位のBRINに置き換えた。正確なGTINとUUIDのB-treeは両方維持した。任意の発行済みUUIDを変更せず、商品名、メーカー、出典と出典内商品ID、確認時刻、元のGTINの桁数を保持する。合成データの元表記は12桁と13桁で、24万件すべてで復元値と証拠項目が一致した。バーコード以外の証拠や任意の出典JSONを追加した容量は未計上。

| 構成 | 24万件分の増分 | イベントなしの合計 | 400 MBまでの残り |
|---|---:|---:|---:|
| BRINの識別表と辞書 | 64.537 MB | 381.144 MB | 18.856 MB |
| 同上＋販売条件2,400件 | 66.044 MB | 382.652 MB | 17.348 MB |
| 同上＋販売条件12,000件 | 71.320 MB | 387.927 MB | 12.073 MB |
| 同上＋販売条件24,000件 | 77.791 MB | 394.399 MB | 5.601 MB |

同じ実行の通常の識別表・辞書は77.095 MB。販売条件の追加容量は、3日分の入れ替え後の実測値を使った。本番の非イベント領域に合算した値は、保持イベント、移行時の一時領域、長期更新の肥大を含まない。代表カテゴリーの確認時刻順40件の読み取りは、BRINのビットマップ走査とソートでローカル実測2.859 ms。BRINは物理配置の相関に依存するため、長期間の混在挿入・更新後の性能や本番での同時負荷は未検証。

## 保持イベントを加えた容量試験

本番事前診断と同じイベント列型と6索引を使い、決済監査118行を模した合成データに、その他の保持イベントを追加した。本文やメタデータは生成したダミー値で、本番のデータ分布から推定したものではない。商品側は24万件のBRIN構成と、1%の期限付き販売条件を使用した。イベントの表容量はTOASTと索引を含む。

| 決済監査118件に加えたイベント数 | イベント物理容量 | 本番非イベント領域と試験データの合計 | 400 MBまでの残り |

| 1,000 | 1.573 MB | 384.200 MB | 15.800 MB |
| 5,000 | 6.627 MB | 389.254 MB | 10.746 MB |
| 10,000 | 12.911 MB | 395.538 MB | 4.462 MB |

同じ隔離クラスタの別の通常テーブルへ20,118件をSQLでコピーし、全列を双方向に比較して差分0件、次の連番は20,119と確認した。コピー先は25,436,160バイト、テーブル作成とコピーを含むWAL増分は31,490,304バイト。これは書き込みのない試験クラスタでのSQLコピーの測定値。既存表との原子的な切替、アーカイブからの復元、本番で必要な一時領域と実際の保持行容量は未検証。

## 移行判断と次の隔離検証

現行方式への24万件一括追加は500 MBを超える。保護対象イベントの物理サイズを実測した後、識別表、辞書、期限付き販売条件、作業領域を含めて予算を決める。全商品に販売条件と名前検索を持たせた試験はイベントを除いても400 MBを超えた。需要時に取得した販売条件は、保持件数に加えて表・索引の実サイズを監視する必要がある。

既存UUIDと既存APIの参照を維持しながら、固定幅GTINと元のバーコード形式の復元、製品変更・消滅、証拠の再取得、旧商品との衝突を確認する。多言語タイトルを必要な場合だけ保存する場合の容量も測定する。

商品試験はUNLOGGEDの合成テーブルを使用した。本番データからの復元、通常テーブルの移行で必要な物理空き容量、本番書き換え時のロック時間は未検証。通常テーブルでの負荷、復元後の件数・索引サイズ、保護対象の一致を別途確認してから本番変更を検討する。


## 停止済みクラスタの物理アーカイブ復元

隔離PostgreSQL 17で商品24万件、期限付き販売条件2,400件、保持イベント20,118件と辞書3表を通常テーブル化した。正常停止後に作った圧縮クラスタアーカイブ（141,447,935バイト）を別ディレクトリに展開し、Unixソケット限定で起動。6表の全行SHA-256、索引、制約、イベント表のRLS・権限と次回採番を照合した。クラスタには試験の補助表もある。測定値はローカルの物理アーカイブサイズで、管理DBの転送料金算定や論理バックアップのサイズは別途確認する。

```sh
GPD33_PG_MODULE=/path/to/pg/lib/index.js \
  node scripts/gpd33_catalog_capacity.mjs /path/to/postgres/bin --demand-only --archive-restore
```

## 通常テーブルで7日分の確認時刻更新を再現

`--demand-only --archive-restore` で通常テーブル化した24万件を1日あたり10%ずつ、7回更新した。各回24,000行で、更新後に通常VACUUMを実施。商品識別・名称・出典を元の24万件と照合し、その後のアーカイブ復元でも6表の内容・索引・権限・採番が一致した。

| 測定対象 | バイト |
|---|---:|
| 読み取りモデルの商品表・索引、更新前 | 60,252,160 |
| 同、7回目のVACUUM後 | 64,888,832 |
| 7回の更新とVACUUMのWAL増分 | 79,220,408 |
| 本番の非イベント既存容量に、更新中の最大商品容量・辞書・2,400オファー・20,118保持イベントを加えた値 | 408,325,267 |
| 更新後の停止済み隔離クラスタの圧縮アーカイブ | 165,169,828 |

保持イベント20,118件の構成は400 MB条件を超える。結果は確認時刻更新の合成試験で、タイトル変更・同時アクセス・保留WAL・本番転送は別途測定する。デプロイ判定には監視側の本番保持行容量と物理空き、当期転送残量を使う。

同じコマンドは `measurements.logged_identity_refresh.retained_scenarios` に、測定した保持イベント容量を更新中の最大容量に足した結果を出力する。`max_retained_relation_bytes_under_400m` は、他の容量が試験条件どおりなら400 MB未満を満たせるイベント表・索引・TOASTの上限。削除行数の目標には使わない。監視の実測と比較する際は、保存必須行を先に確定し、WAL・作業領域・転送残量を個別に確認する。

2026-11-26の再実行では更新中のイベント以外の合算値は382,889,107バイト。保持イベント表の上限は17,110,892バイトだった。決済監査118件に他のイベントを1,000／5,000／10,000／20,000件加えた各実測サイズを使うと、合算は384,461,971／389,516,435／395,799,699／408,341,651バイト。初めの3条件は400 MB未満、4条件とも500 MB未満。いずれもディスク空きと当期転送量を証明する値ではない。復元の一致確認も再度合格した。
