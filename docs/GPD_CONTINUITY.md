# GPD 継続開発と引き継ぎ

基準日 2026-11-25。設計判断は [恒久開発指針](GPD_DEVELOPMENT_CHARTER.md)、各機能の評価と完了条件は [ロードマップ](GPD_ROADMAP.md) に従う。セッションや自動タスクを再開したら、最初に本ファイル、GitHubの最新コミットと検証結果、現在の本番状態を確認する。

## 現在の開発段階

- v33.0の分析用管理APIに、販売業者が認証して報告した受理・注文・取消の集計を追加した。実装とローカル検証は [販売業者への引き渡し](MERCHANT_HANDOFFS.md) を参照する。
- GitHub上の統合開発と本番の整理は並行で進める。本番から隔離したPostgreSQL、外部サービスのモック、GitHub Actionsを使う。運用者が発行した期限付きトークンで、買い手が引き渡しの最新状態を確認できる経路を追加し、WorkerとPostgreSQLを通したテストで照合済み実績との区別を確認した。
- 部品の販売業者検索に、メーカーと型番が一致し、検証済み販売業者が対象国への配送と在庫を明示している引き渡し候補を追加した。検索から引き渡し、注文・取消報告、追跡、集計までを隔離環境で検証する。候補を使う前に実際の価格・在庫・配送条件と買い手の同意を確認する。
- 公開鍵を登録した販売業者の報告にEd25519署名を必須化した。隔離環境で検索、引き渡し、署名検証、注文・取消報告、買い手の追跡、再送を通しで検証した。次は外部注文台帳と契約済み仲介料の照合に必要な証拠を扱う。
- 12月2日の利用期間更新後に、無料枠、DB容量400 MB未満、物理作業領域、稼働条件を実測する。条件が整ったら、Worker、マイグレーション、必須テストがそろい、検証に成功した最新の安定コミットを特定して投入する。リリース番号やカレンダーだけで適否を決めず、投入したコミットと本番ヘルスの結果を記録する。
- 本番Supabase内のログ整理と完了後の通常VACUUMは [運用手順](../supabase/maintenance/IN_DATABASE.md) に沿って継続中。全DBの外部エクスポートは使用しない。非公開の本番数値や資格情報はこのファイルに記録しない。

## 統合開発の再開

- `tests/gpd33_worker.mjs` はMCP、公開API、x402、専門機能と販売業者一覧を検証する。`tests/gpd33_database.mjs` は隔離PostgreSQLで候補の検索から買い手認証、引き渡し、署名付き報告、取消、追跡、テスト台帳との照合までをつなぐ。`node tests/gpd33_reconcile.mjs` は入金・返金の照合を再検証する。
- 前回に続いて、[ロードマップの検証範囲](GPD_ROADMAP.md#統合検証の範囲と再開地点) とリリースCIを読む。買い手の経路は既存Authの確認が済むまで無効のまま。モック台帳を実績として扱わない。次の独立工程は外部台帳の安全な取込、一般商品とMerchantオファーの照合、販売業者接続・エージェント利用の観測。進められる工程を並行に処理し、テストを結合してから結果を記録する。

今回の統合範囲は [エージェント登録](GPD_AGENT_ONBOARDING.md)、[販売業者候補の取り込み](GPD_SELLER_DISCOVERY.md)、[署名付き台帳の照合](GPD_RECONCILIATION.md)。全24カテゴリーに共通する検証済みGTINのオファー照合から、買い手確認、配送・在庫条件、署名済み注文結果、テスト入出金の照合までを通し試験に加えた。次回は合意済み販売業者のフィード取り込みと一般商品のオファー登録の型・制約の確認、実台帳の取得経路、導入と収益を探索配分に反映する指標を並行で進める。発行者の署名鍵や実契約がない環境ではテスト台帳のみを使う。

### 買い手・販売業者の観測を探索に反映

検証済みGTINで新規に受け付けた引き渡しにカテゴリーを記録し、過去7日の買い手アカウントと現在受理・注文報告済みの販売業者をカテゴリー単位で重複排除して数える。2アカウント未満のカテゴリーは集計から外す。`GPD_BUYER_GROWTH_SIGNALS=1` の場合だけ、探索配分の裁量枠に加点する。全カテゴリーの巡回枠と外部API予算はそのまま。管理者起点の引き渡しや識別を確定できない案件は加点対象外。集計は観測されたアカウントと販売業者の反応であり、実ユーザー数・取引成立・売上は別途測定する。設定は既定で無効。

- [提携先の一括レビュー](GPD_PARTNER_REVIEW.md) は承認済み商品フィードと署名付き台帳を、指定したHTTPS取得先から取得・検証し、両方の検証が済んだ時点で非公開レポートを保存する。取得失敗・同時実行・同一スナップショット再送は `node tests/gpd33_partner_review.mjs` で再現できる。実運用の取得先・契約・発行者設定は未接続。次は承認済みソースでの実取得、正規オファーへの権限付き登録、独立した発行者の実績と収益照合を進める。

販売業者のフィード登録は専用経路で受け付ける。確認済み販売業者のキーと本文の販売業者IDが一致する場合に、SKUごとに新規登録または更新する。更新は既存のオファーIDを保ち、古い観測・重複・識別矛盾を飛ばす。隔離環境ではフィード更新後も既存の引き渡しの参照が有効なことを確認する。実運用の承認済みフィード・台帳・定期ジョブは未設定。

オファー登録、GTIN検索、引き渡しで、販売業者の在庫・配送の観測を直近7日（時計差の許容は未来5分）にそろえた。鮮度を証明できないものは検索比較に残すが、新規のGTIN引き渡しには使用しない。隔離テストは古い観測、観測なし、不自然な未来時刻と再送を検証する。[仕様](MERCHANT_HANDOFFS.md)

同一のレビューを再利用できるのは、保存済みレポートと承認・発行者設定が一致する場合に限る。オファー登録に非公開の受領記録を指定した場合は、Workerが確認済みの同じ登録を再送しない。取得から署名付き台帳照合、承認付き登録、再送までの結合試験は `node tests/gpd33_partner_review.mjs`。実運用の提携先設定、取引、決済は引き続き未接続。

本番区分のHTTPS台帳取得と保存済みレビューの再利用には、署名の一致に加え、観測が直近24時間（未来の時計差は5分まで）であることを求める。履歴照合用のオフライン経路は既存のまま。

承認済みフィードの数量をWorkerとPostgreSQLまで引き継ぎ、GTIN検索と新規引き渡しの双方で複数個の依頼に十分な報告数量を求める。数量が未報告の更新では古い数量を使わない。再送、非GTIN部品、失効した観測についても隔離テストを実行する。[手順](MERCHANT_HANDOFFS.md)

一般商品の購入判断でも在庫数量の不足・未確認を理由として返し、複数個の希望数量をGTINオファー検索に引き継ぐ。購買判断、オファー検索、引き渡しの数量制約を一連の経路で維持する。

eBayの配送用在庫と店頭受け取りを区別し、掲載終了を購入不可として扱う。単一の配送条件から得たeBayの数量は推定として返し、複数購入に必要な報告済み在庫数には代用しない。在庫状態は完全一致で判定し、在庫なしに相当する状態を在庫ありに含めない。追加の外部リクエストは発生しない。

一般商品の購買判断は、説明文のない有効なGTINだけのGET・POSTでもx402の署名検証へ進む。照合が成立したGTINは検索・引き渡し経路に引き継ぐ。無効なGTINと不正な支払い署名は隔離テストで拒否を確認する。

eBay接続なしの一般商品購買判断でも、GTINを既存カタログと照合し、検証済み商品なら販売業者検索へのリンクを返す。外部APIは追加せず、認証情報なしの場合のDB照合は1回・最大2行の最小項目。購入可能の判定には引き続きオファーの証拠が必要。

一般商品の購買判断では、GTINに加えてメーカーが指定されている場合は両方の一致を確認する。確認できたメーカー指定を販売業者検索へ引き継ぎ、矛盾するカタログやオファーから購入経路を提示しない。

GTIN購買判断の新品・中古などの状態指定を販売業者検索へ引き継ぐ。状態が未報告・不一致のオファーは状態指定付きの検索から除く。色・サイズ・容量・入数を個別に指定した依頼では、販売業者側でもその条件を確認できるようになるまで、自動引き渡し用の検索リンクを控えて理由を返す。

買い手APIに `condition` を追加し、新規依頼の現在の状態と買い手の指定をDBの同じ処理で照合する。指定は販売業者の受付一覧にも届く。状態が変わった後の既存依頼の再送と、同じIDで指定を変えた依頼を区別する。

承認済みフィードで報告された商品状態を保持する。新しいフィードで状態が未報告なら未確認として記録する。本番の制約、認可、実データでの適用は移行条件を満たした後に確認する。

## 買い手獲得と取引証拠の統合

公開探索文書、MCP初期化・ツール一覧、OpenAPI、MCP Registry候補の整合性をオフラインで検証する。外部レジストリへの公開は稼働中のバージョンとビルドを確認した手動実行に集約した。認証済みの買い手は `GET /v1/handoffs` で直近30件以内を確認できる。`request_id` で特定の依頼を検索できる。買い手の範囲は認証結果で決まり、注文参照ハッシュや追跡トークンは返さない。

外部注文の署名で認可された組み合わせを基に、DB内の引き渡し証拠を最大100件取得して署名する。隔離DBの通し試験では同じ経路で、販売業者の報告・取消、契約済み手数料の入金・返金、探索配分用の集計まで確認した。再開時は `node tests/gpd33_registry_draft.mjs`、`node tests/gpd33_export_handoff_evidence.mjs` と隔離PostgreSQL 17の `node tests/gpd33_database.mjs` を実行する。

次は採用済み販売業者と注文・最終入金の正規発行元を接続し、同意範囲内の取引で端から端まで検証する。x402の情報提供料については、確定済みSolana送金とAPI支払い記録を照合する独立処理が残る。外部登録、顧客獲得、実注文、実入金、本番移行はこの統合検証では発生していない。

## 次の実装単位

1. **一件の実購買判断を収益までつなぐ。** 販売業者の受理から注文・取消までの試験データを使って通しで再現できるようにする。相手が同意した実案件で使えるテスト計画をまとめる。買い手の権限確認と販売業者の認証、照合に必要な参照、外部からの署名付き結果を整える。売り手の申告だけで商品取引成立や仲介収益を計上しない。
2. **取引と入金を照合する。** x402の情報提供料と商品代金・仲介手数料を区別し、成功、失敗、再送、取消、返金の検証を統合する。契約条件が確定している手数料だけを照合対象にする。決済記録と実収益の照合、および既存のMCP、API、x402と専門機能の回帰テストを同じ変更で確認する。
3. **購入可能な商品と利用者を増やす。** 全24カテゴリーで検証済み商品、在庫・配送オファー、必要な識別根拠の欠けを測定する。既存無料ソースとMerchantフィードを使い、地域、通貨、言語を明示した実取引の成功率で探索を改善する。公開OpenAPI、MCPの資料、互換性検証を先行し、エージェントの認知と導入を計測する。
4. **継続運用を自動化する。** 状態変化、データ品質、障害復旧、容量と転送量を検証し、取引量と収益の実績を探索配分へ反映する。無料枠内で利用可能な経路を優先する。

各実行で、関連する実装、テスト、修正、統合、検証を一つの流れで進める。部分実装を本番実証済みとしない。変更を保存するときは本ファイルとロードマップに、完了した工程、残る障害、次に検証する結果を追記する。外部契約、費用発生、実商品の注文、資金移動は権限と承認が確認された範囲でのみ行う。
